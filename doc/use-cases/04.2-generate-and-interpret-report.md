# Use Case: 04.2 - Generate and Interpret Mutation Testing Results (Extended)

## Description
This use case describes how to generate **structured mutation testing reports** and **analyze them in depth** by inspecting both the **production code** and the **test suite**.

The goal is to:
- Obtain **structured reports** of mutation testing results
- Analyze **strictly survived mutants** to understand **test weaknesses**
- Classify survived mutants and provide concrete fixes.
- Provide **specific reasoning** and **concrete fixes** for tests or code when applicable

---

## Actor
**RooCode Agent**

---

## Preconditions
- A mutation testing session has been performed, and a session file (e.g. `'session.sqlite'`) containing the results is available.
- The codebase has been cleaned and verified according to **Use Case 04.1 - Pre-evaluation Cleanup**.

---

## Flow

### 1. Generate Mutation Reports
- Agent generates a **detailed HTML mutation testing report** from the available session data. This can be achieved by running the command `cr-html <session-file> > <output-file>.html`.
- **Verification:** Agent confirms the report exists and contains **valid, readable content**.
- **Troubleshooting:** If `cr-html` fails due to a database schema mismatch (e.g., `sqlite3.OperationalError: no such column`), it indicates a version incompatibility between the `cosmic-ray` version that created the database and the one being used to generate the report. In this case, the agent should delete the session file and regenerate it using the currently installed `cosmic-ray` version. The following commands can be used:
    ```bash
    del <session-file>
    cosmic-ray init <config-file> <session-file>
    cosmic-ray exec <config-file> <session-file>
    cr-html <session-file> > <output-file>.html
    ```

- Agent generates a **structured summary** of the mutation testing results.
- **Verification:** Agent extracts **high-level metrics** such as total mutants, killed mutants, surviving mutants, and mutation score.

---

### 2. Identify Mutant Sets
The agent separates mutants into the following **disjoint sets**:

- **Strictly survived mutants**
  - Status: `'SURVIVED'`
  - Explicitly excluding: `'KILLED'`, `'NO_COVERAGE'`, `'EQUIVALENT'`, `'ERROR'`, `'TIMED_OUT'`

- **Killed mutants**
  - Status: `'KILLED'`

All subsequent steps rely on this separation.

---

### 3. Analyze and Report Strictly Survived Mutants

The agent must **analyze the relevant code and tests** for each **strictly survived mutant** and document the findings in two separate files.

#### Output A: **Survived Mutants Grouped by Mutation Operator**

- **File:** `survived_mutants_by_operator.md`
- **Grouping order:**
  1. **Mutation operator**
  2. **File path**
  3. **Mutant entries**

Each entry must include:
- **File path**
- **Line number(s)**
- **Mutation operator**
- **Original → mutated code**
- **Classification:** 'Fix code', 'Fix tests', or 'Unknown'
- **Reasoning:** A detailed explanation for the classification.
- **Fix:** A concrete code or test fix.

---

#### Output B: **Survived Mutants Grouped by File**

- **File:** `survived_mutants_by_file.md`
- **Grouping order:**
  1. **File path**
  2. **Mutation operator**
  3. **Mutant entries**

Each entry must include the **same information** as Output A.

---

## Postconditions
- **Exactly three Markdown files** are produced:
  1. `survived_mutants_by_operator.md`
  2. `survived_mutants_by_file.md`
- All **strictly survived mutants** are documented **twice** (once in `survived_mutants_by_operator.md` and once in `survived_mutants_by_file.md`), and include a classification, reasoning, and a fix.
- All reasoning is grounded in **actual code and tests**.
